# OPS-003 · Authentication and organization onboarding

## Routes

| Route              | Behavior                                                                       |
| ------------------ | ------------------------------------------------------------------------------ |
| `/`                | Existing public landing page, with sign-in and signup links                    |
| `/login`           | Email/password sign-in with the Supabase browser client                        |
| `/signup`          | Email/password signup; shows confirmation guidance when no session is returned |
| `/auth/callback`   | Exchanges the Supabase PKCE code and redirects to onboarding                   |
| `/auth/confirm`    | Optional token-hash email confirmation endpoint                                |
| `/onboarding`      | Authenticated workspace list and workspace creation form                       |
| `/{org}/dashboard` | Requires a verified session and an ACTIVE organization membership              |

The `(platform)` layout uses `getClaims()` to verify identity. The organization layout and the dashboard's data loader call NestJS to authorize the requested slug. React request caching only deduplicates reads in one render; no organization response is cached across users or requests. Data operations must continue to check membership independently of a layout.

## Windows setup

From the repository root, after installing the pinned Node/pnpm versions:

```powershell
if (-not (Test-Path apps/web/.env.local)) { Copy-Item apps/web/.env.example apps/web/.env.local }
if (-not (Test-Path apps/api/.env)) { Copy-Item apps/api/.env.example apps/api/.env }
pnpm install --frozen-lockfile
pnpm db:up
pnpm db:migrate:deploy
pnpm dev
```

Edit the ignored environment files before starting the apps:

- Web: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
- API: the same project as `SUPABASE_URL`. The API verifies asymmetric JWTs using public JWKS; no Supabase API key is required.
- Both: the frontend's `NEXT_PUBLIC_API_BASE_URL` must point to the NestJS `/api/v1` base; `CORS_ORIGINS` must allow the web origin.
- The local Compose PostgreSQL URLs in the API example work with hosted Supabase Auth. A hosted database is optional for local development.

Use the public `sb_publishable_...` key. This implementation does not need a secret/service-role key or a JWT signing secret. Public Next.js variables are embedded during the build, so configure them before a deployment build. JWT verification uses pinned `jose` 6.2.12. Supabase package versions are pinned: `@supabase/ssr` 0.12.7 and `@supabase/supabase-js` 2.118.0.

In the Supabase Auth dashboard:

1. Enable email/password signup and email confirmation.
2. Set the Site URL to the frontend origin (locally `http://localhost:3000`).
3. Allow `http://localhost:3000/auth/callback` and the equivalent production URL as redirect URLs.
4. Set a minimum password length of 12 to match the signup form.

The normal confirmation email follows the PKCE callback and should be opened in the browser that started signup. If your project supports custom email templates and you need token-hash confirmation, use `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`; the optional confirmation route also always redirects to onboarding. Neither callback accepts an arbitrary redirect destination.

## Organization API contract

Every organization endpoint requires `Authorization: Bearer <Supabase access token>`.

| Method and endpoint                          | Result                                                                                            |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `GET /api/v1/organizations`                  | Active memberships for the verified user, excluding archived organizations/deactivated profiles   |
| `POST /api/v1/organizations`                 | Creates a profile if needed, the organization, and its ACTIVE OWNER membership in one transaction |
| `GET /api/v1/organizations/:slug/membership` | Returns organization summary only for an ACTIVE membership                                        |

Creation accepts only `{ "name": "Acme Engineering", "slug": "acme-engineering" }`. Name is trimmed and must have 2–120 characters. Slug is trimmed, must already be lowercase, has 3–80 characters, uses lowercase letters/numbers separated by single hyphens, and cannot collide with application routes. The backend derives user and owner role from the verified identity; extra request fields are rejected.

Creation returns `{ id, name, slug }`. Listing returns `[{ organization: { id, name, slug }, role }]`; membership lookup returns `{ organization: { id, name, slug }, role }`. A duplicate slug returns 409; invalid fields return 400; missing/invalid tokens return 401. Missing, archived, and inaccessible organizations all return 404. Deactivated profiles cannot create organizations (403). Auth service outages return 503. Responses, including errors, use `private, no-store`.

The Next.js layout verifies Supabase `getClaims()`. NestJS independently verifies asymmetric signatures, issuer, audience and required expiry with `jose` against public JWKS, then checks the authenticated role, non-anonymous identity, UUID subject/session and application revocation. User-editable metadata is never used for authorization. `getSession()` is used only to retrieve a bearer token, which the API verifies again.

OpsPilot logout first calls `POST /api/v1/auth/logout` (204), which stores the verified `session_id` in an API-only revocation table, then signs out the current Supabase session and clears browser cookies. Every protected API request checks this table, so replayed and refreshed tokens for that session return 401 immediately after logout completes. A new sign-in creates a different session and remains valid. Tombstones are retained indefinitely because refresh tokens can outlive the original access token; deployment maintenance must preserve this guarantee. This adds a database lookup to every protected request. Logout fails visibly if the API cannot persist revocation. Supabase sign-outs outside this application and other devices are not covered by this local-session endpoint. Membership and profile deactivation checks are also read on each tenant request.

## Database access boundary

The new SQL migration enables RLS on all application tables with no browser policies. NestJS uses a server-only Prisma connection as table owner (or a suitably privileged server role); Supabase browser clients only use Auth. Do not grant browser Data API policies that bypass these API checks. Apply the committed Prisma migrations to the intended database using its server credentials; no hosted database is changed automatically.

## Verification

```powershell
pnpm db:validate
pnpm format:check
pnpm lint
pnpm typecheck
pnpm build
```

The integration suite needs a disposable migrated database with role-creation privileges, and refuses to run without an explicit `TEST_DATABASE_URL`. It inserts isolated test rows and should never be aimed at a development or production database containing real data.

```powershell
$env:DATABASE_URL = 'postgresql://opspilot:opspilot_test@localhost:55437/opspilot_test?schema=public'
$env:DIRECT_URL = $env:DATABASE_URL
pnpm db:migrate:deploy
$env:TEST_DATABASE_URL = $env:DATABASE_URL
pnpm test:integration
pnpm test:platform
Remove-Item Env:TEST_DATABASE_URL
Remove-Item Env:DATABASE_URL
Remove-Item Env:DIRECT_URL
```

CI provisions PostgreSQL, applies migrations and runs these HTTP-level checks with cryptographically signed tokens and a local JWKS endpoint. Coverage includes invalid signatures, expiration/issuer/audience/role, DTO validation and owner spoofing, transaction rollback, concurrent slug conflicts, cross-tenant access, inactive memberships, archived/deactivated records, logout replay and refreshed-token denial, pre-onboarding logout, and RLS on direct database queries. No live Supabase users are created by the tests.

Manual acceptance: landing remains at `/`; unauthenticated platform requests redirect to `/login`; login goes to onboarding; signup without a session shows email confirmation guidance; a newly created workspace opens its dashboard; an outsider cannot open its URL; sign-out returns to login.
