# OPS-004 — Service management and ownership

## Completed workflow

An active workspace member can browse the real service catalog and open service details. Workspace owners/admins can create, edit and archive services, choose active organization members as service owners, and remove assignments. Ordinary members see the ownership list without management controls. The existing Supabase identity and NestJS authorization boundary remains in place.

The ownership selector loads real records from the organization member directory. It contains no hard-coded people or manual user-ID input. Successful changes refresh server data. Errors are announced, pending requests disable controls, and uncertain network results ask the user to refresh before retrying.

## API and permissions

All endpoints below require a verified bearer token. Every request resolves the caller's ACTIVE membership, excludes deactivated users and archived organizations, and scopes service IDs to that organization.

| Endpoint                                                         | Active MEMBER      | Active OWNER / ADMIN              |
| ---------------------------------------------------------------- | ------------------ | --------------------------------- |
| `GET /api/v1/organizations/:slug/services`                       | Read               | Read                              |
| `GET /api/v1/organizations/:slug/services/:id`                   | Read               | Read                              |
| `POST /api/v1/organizations/:slug/services`                      | 403                | Create                            |
| `PATCH /api/v1/organizations/:slug/services/:id`                 | 403                | Edit                              |
| `DELETE /api/v1/organizations/:slug/services/:id`                | 403                | Archive                           |
| `GET /api/v1/organizations/:slug/services/:id/owners`            | Read active owners | Read active owners                |
| `PUT /api/v1/organizations/:slug/services/:id/owners/:userId`    | 403                | Assign active member; 204         |
| `DELETE /api/v1/organizations/:slug/services/:id/owners/:userId` | 403                | Remove assignment; 204            |
| `GET /api/v1/organizations/:slug/members`                        | 403                | List active members for selection |

The directory returns `{ userId, displayName, email, role }`; owners add `assignedAt` as an ISO timestamp. Directory access is limited to managers because it exposes organization contact information.

Missing or invalid authentication returns 401. Inactive/foreign callers and foreign, missing or archived services return 404. An assignment target must be ACTIVE in the same organization and have a non-deactivated profile; ineligible/missing targets return 404. Repeated assignments and removals are idempotent. Removing a former member's stored assignment remains possible for authorized managers.

Names, slugs, description length, tier/status enums and HTTP/HTTPS runbook URLs are validated. Service slugs and organization IDs cannot be changed through PATCH. A duplicate service slug in one organization returns 409. Operational status remains manually declared.

## Persistence and concurrency

OPS-002 already supplies the service and ownership tables and composite tenant foreign keys, so this task adds no schema migration. Ownership writes lock the active service row inside their transaction. Service archival updates the same row; concurrent archive/assignment requests therefore serialize. Archived services cannot receive new ownership writes.

Archival preserves the service row, assignments and incident references. Inactive/deactivated owners are excluded from the current ownership list while their historical relationship remains stored. Explicit removal deletes the assignment; this is not a separate audit-log feature.
