# OPS-007 — Incident Collaboration & Audit Hardening

## Scope
- Organization-scoped responder assignment, removal and listing.
- Service linking/unlinking on incident updates.
- Monotonic audit-event ordering via a bigint sequence and additive migration.
- Incidents page responder controls, affected-service editor and existing lifecycle/timeline UX.
- Integration tests for member permissions, inactive/foreign targets, idempotency, service changes and audit ordering.

## Routes
All routes require a verified Supabase session and active organization membership.
- `GET /api/v1/organizations/:orgSlug/incidents/:id/responders`: all active members
- `PUT /api/v1/organizations/:orgSlug/incidents/:id/responders/:userId`: OWNER/ADMIN, 204
- `DELETE /api/v1/organizations/:orgSlug/incidents/:id/responders/:userId`: OWNER/ADMIN, 204
- `PATCH /api/v1/organizations/:orgSlug/incidents/:id`: OWNER/ADMIN; adds optional `serviceId` UUID or null

All writes use incident row locking, audit events in the same Prisma transaction, and validate membership and same-organization resource ownership. Assigning/removing the same user twice is idempotent. Removed responders are retained as historical records.

## Migration
`apps/api/prisma/migrations/20261028233000_ops007_event_sequence/migration.sql` backfills existing events by timestamp and UUID (best possible reconstruction), adds a bigint global sequence and index, and preserves all rows. New ordered event inserts run after acquiring the incident's row lock. PostgreSQL sequences are monotonic for committed events per incident, but can have gaps after transaction rollbacks.

Do not execute migration against production data without backup and a reviewed deployment plan.
