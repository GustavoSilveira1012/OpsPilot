# OPS-005 — Incident Management API

## Scope

OPS-005 implements authenticated, organization-scoped incident creation, search, read, lifecycle updates, and collaborative notes. The Next.js incidents interface is planned separately for OPS-006. This release is API-only; it does not claim automated detection or real-time monitoring.

## Endpoints and authorization

All endpoints have the `/api/v1` prefix and require a verified Supabase bearer token. Every request resolves a live ACTIVE organization membership and excludes deactivated users or archived organizations.

| Route | ACTIVE MEMBER | OWNER / ADMIN |
| --- | --- | --- |
| `GET /organizations/:orgSlug/incidents` | Read | Read |
| `GET /organizations/:orgSlug/incidents/:id` | Read & timeline | Read & timeline |
| `POST /organizations/:orgSlug/incidents` | 403 | Create |
| `PATCH /organizations/:orgSlug/incidents/:id` | 403 | Update |
| `POST /organizations/:orgSlug/incidents/:id/notes` | Add note | Add note |

Inactive and cross-organization users receive 404 on tenant-scoped resources. Unknown and foreign incident IDs also receive 404. Malformed UUIDs and unexpected payload properties return 400.

## Contracts

Creation accepts `{ title, summary?, severity?, serviceId? }`. The server assigns organization-scoped incident numbers, status `INVESTIGATING`, creator ID, and creation timestamp. Default severity is `SEV3`. A linked service must be active and belong to the same organization. `GET` list returns `{ items, total }` with optional `status`, `severity`, `serviceId`, `offset`, and `limit` query parameters. Limits range 1–100 and default to 25.

Updates accept `{ status?, severity?, summary? }`. Only changed fields generate timeline entries; a no-op update is valid and creates no events. Status transitions permitted:
- INVESTIGATING → IDENTIFIED, MONITORING, RESOLVED
- IDENTIFIED → INVESTIGATING, MONITORING, RESOLVED
- MONITORING → INVESTIGATING, IDENTIFIED, RESOLVED
- RESOLVED → INVESTIGATING (reopen)

When resolved, `resolvedAt` is set; reopening clears the current `resolvedAt`, while earlier resolution events remain in the activity timeline. Changing severity or summary alone does not alter resolution time.

Notes accept `{ message }` with trimmed length 1–4000 and return a persisted event with `MESSAGE_ADDED`. Notes are append-only for any active organization member.

## Atomicity and security

Creation increments `Organization.nextIncidentNumber`, creates the incident, and inserts `INCIDENT_CREATED` in one Prisma transaction. Concurrent increments on the organization row serialize in PostgreSQL. The database enforces unique `(organizationId, number)`.

Lifecycle updates acquire a row lock on the incident before reading and modifying its current state; the incident update and audit events commit atomically. Notes likewise lock the incident row to order writes. Timeline ordering is `occurredAt` ascending followed by event ID; historical events are never rewritten or deleted via OPS-005.

NestJS always derives `actorUserId`, `createdByUserId` and organization ID from verified auth and membership, never from caller input. Linked services are tenant checked. Response caching is disabled. This release does not implement incident responder assignment, automation, or a dedicated UI.

## Verification

From repo root:
```powershell
pnpm install --frozen-lockfile
pnpm db:validate
pnpm format:check
pnpm lint
pnpm typecheck
pnpm build
```

Run integration tests **only against an isolated migrated test database**; never point these commands at production:
```powershell
$env:DATABASE_URL = 'postgresql://opspilot:opspilot_test@localhost:55437/opspilot_test?schema=public'
$env:DIRECT_URL = $env:DATABASE_URL
pnpm db:migrate:deploy
$env:TEST_DATABASE_URL = $env:DATABASE_URL
pnpm test:integration
pnpm test:platform
Remove-Item Env:TEST_DATABASE_URL
Remove-Item Env:DIRECT_URL
Remove-Item Env:DATABASE_URL
```

The incident integration suite uses signed local Supabase-compatible JWT fixtures, exercises numbering under concurrency, validation, tenant isolation, access controls, lifecycle transitions, audit events, notes and inactive members. GitHub CI supplies disposable PostgreSQL, validates and builds the monorepo, and runs both API and platform test suites.
